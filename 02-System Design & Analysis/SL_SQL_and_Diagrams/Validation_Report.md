## Independent review correction — 29 October 2026

An audit of the original validation script found that its test named “Unknown category FK blocked” supplied `model_source=dominant_color` and `attribute=product_type`. That input was invalid under `ck_visual_prediction_08`, so the original rejection did **not** verify the category foreign key. The test was independently repeated using a valid `model_source=primary_cv` with an unknown `predicted_category_code=made_up_class`; the SQLite surrogate rejected the row with `FOREIGN KEY constraint failed`. A separate test confirmed that `dominant_color` with `product_type` fails the intended CHECK.

The ledger row now reflects the corrected isolated retest. The **140 test-case count** refers to the prior reported surrogate/static suite, with one test's evidence corrected on review; it does not represent PostgreSQL runtime execution. The authoritative PostgreSQL DDL itself was not changed.

Additional design decision: `product_listing.image_origin` currently enforces the single value `fashion_product_images_small`. This may be correct for a dataset-only demonstration, but FR-001 permits seller-provided images and does not expressly establish that all uploads originate in the dataset. Clarify provenance policy with the team before implementation rather than automatically broadening the allowed values.

## Execution boundaries and test data

The SQLite surrogate was created exclusively in `:memory:` from type-transformed emitted DDL. Five `test_class_1` … `test_class_5` category codes were used only in that ephemeral simulation to exercise foreign keys; they **are not** fashion categories and were **not** written to any deliverable seed script. SQLite differs from PostgreSQL in type affinity, constraints, timestamp semantics and dialect features. Application behavior and ML outputs were not executed.
